## 本版解决的问题

此前邮件里的“确认邮箱”按钮实际只打开页面，仍需页面主动确认；原申请标签页的容量也可能仍显示旧值。邮件测试身份可以确认成功，却按设计不占正式名额。三者容易被误解为确认失效，设备切换本身不会使签名失效。

- 中英 HTML/纯文本邮件明确“打开确认页 → 点击确认订阅 → 等待成功”，保留 24 小时有效期及可复制的原网址。
- 确认页突出最后一步按钮，成功后才提供偏好编辑；GET、预取或邮件扫描仍无确认/退订副作用。
- 返回原标签页的 focus/visibility 只刷新公开名额，防止容量停留在确认前结果。
- 订阅页切换中英文保留签名参数；离开该页不向其他页面传播参数。
- 签名响应区分 public/test，测试页明确不进入正式周报、不占名额；不自动将测试身份转正式。
- 保留容量原子控制、代际/epoch、防重复投递、unknown/uncertain 不自动重发、退订与抑制，以及现有生产配置与任务。

发布前，2026-10-13 用户报告用新邮箱完成公众确认后，页面已确认人数为 1。该报告说明公众确认路径有实际成功案例；本版是否上线由上述部署/tag 凭据证明，用户反馈不能取代完整验收。公开记录不保留邮箱、签名链接、邮件内容或订阅行。

## 版本与接续

GitHub 远端 `v1.0.0` tag 是本版源码的正式权威标识；`package.json` 的版本号只是工程元数据。可在 [仓库 tags](https://github.com/AutoGenUI/ag-ui.ai/tags) 查询，或只读执行：

```sh
git ls-remote --tags origin 'refs/tags/v1.0.0' 'refs/tags/v1.0.0^{}'
```

带注释 tag 的原始 tag 对象 SHA 与解析后的 commit SHA不同，记录 release commit 时用解析结果。tag 还未创建时没有输出，不能因此假设已发布。

Sites 的数字版本序号由平台生成，与语义版本独立；v1.0.0 不意味着 Sites version 1。使用原项目的 `get_site` 和对应 `get_deployment_status` 查询实际部署；保存版本不等于部署成功，GitHub push 也不等于上线。完整步骤见 [部署维护](../operations/deployment-maintenance.md)。

本版不迁移 schema。新客户端要求签名响应中的身份字段，回退时必须恢复匹配的客户端/Worker并刷新页面；混合版本报错不代表确认事务未执行，不重复发信或修改 `is_test` 来消除提示。日常接手先核对实际远端、工作区、Sites 版本、运行状态和授权范围，继续以 main 迭代，保留公开 [维护手册](../operations/README.md) 与私有配置的边界。
